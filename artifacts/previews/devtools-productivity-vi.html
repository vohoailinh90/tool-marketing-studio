Các lệnh Git theo việc cần làm

Bạn vừa sửa hai file nhưng chỉ muốn lưu một thay đổi. Hãy nhìn Git theo ba trạng thái: file đang sửa, nội dung đã chọn cho lần lưu tới và lịch sử đã commit. Lệnh đúng phụ thuộc vào trạng thái bạn muốn thay đổi.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

git init tạo kho mới; git clone lấy một kho có sẵn. Trước khi lưu, dùng git status xem file nào thay đổi, git diff xem phần chưa stage và git diff --staged xem phần sẽ vào commit. git add app.py chọn nội dung hiện tại của file; nếu sửa tiếp, cần add lại để chọn phiên bản mới.

git switch -c fix-title tạo và chuyển sang nhánh làm việc. git fetch cập nhật thông tin từ remote; đọc diff trước khi tích hợp. git push gửi commit, không gửi mọi file chưa commit trong thư mục.

Giới hạn cần nhớ

Quy trình làm việc với Git

Hai người cùng sửa dự án không cần dùng chung một thư mục. Mỗi người có kho Git cục bộ, tạo commit riêng rồi trao đổi lịch sử qua một remote. Quy trình tốt giúp thay đổi được xem xét trước khi ghép vào nhánh chung.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

Ví dụ Lan sửa thông báo lỗi trên nhánh riêng. Lan kiểm tra ứng dụng, chọn thay đổi và commit với lời giải thích. Minh vẫn có thể làm việc trên máy khác mà không chờ Lan hoàn thành.

Sau git fetch, Lan thấy nhánh chung có commit mới của Minh. Lan chọn merge hoặc rebase theo quy ước nhóm, xử lý xung đột nếu có và chạy kiểm tra lại. Khi push nhánh, Lan mở pull request để người khác xem diff. Pull request là tính năng của nền tảng cộng tác; Git tự nó quản lý commit, nhánh và việc tích hợp lịch sử.

Đọc JSON lồng nhau bằng sơ đồ

Một phản hồi API có nhiều cấp khiến bạn khó biết giá trị nằm ở đâu. JSON Crack là một lựa chọn để xem cấu trúc bằng đồ thị. Trước hết cần hiểu quan hệ giữa object, array và giá trị; hình đẹp không thay thế kiểm tra dữ liệu.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

Với dữ liệu {"order":{"items":[{"qty":2}]}}, đường tới số lượng là order.items[0].qty. Object dùng tên khóa; array dùng vị trí, bắt đầu từ 0. Một nhánh mở rộng trên đồ thị giúp lần theo đúng cấp khi dữ liệu dài.

Bạn có thể thử công cụ bằng dữ liệu giả, tìm một trường rồi đối chiếu đường dẫn với JSON gốc. Khi thiếu trường, cần phân biệt khóa không tồn tại, giá trị null và array rỗng. Ba trường hợp này thường dẫn đến cách xử lý khác nhau trong chương trình.

Nhìn hình thử trả lời

Trong ví dụ, items là object hay array? qty nằm ở cấp nào?

Xem đáp án

items là array. qty nằm trong object ở phần tử số 0 của array này.

Giới hạn cần nhớ

Sơ đồ cấu trúc không chứng minh dữ liệu đáp ứng schema hoặc quy tắc nghiệp vụ. Chưa kiểm chứng chế độ lưu trữ/xử lý dữ liệu của dịch vụ hiện hành; chỉ dùng dữ liệu giả khi thực hành.

Xem sâu hơn

JSON không có comment theo chuẩn và tên khóa object phải là chuỗi. Cú pháp hợp lệ vẫn có thể chứa kiểu không mong đợi, chẳng hạn qty là chuỗi "2" thay vì số 2.

Git và GitHub giải quyết việc gì?

Git là hệ thống quản lý phiên bản phân tán. Kho cục bộ chứa lịch sử để so sánh, tạo nhánh và commit. Remote có thể là GitHub, một dịch vụ khác hoặc kho do nhóm tự vận hành.

GitHub lưu kho và cung cấp pull request, issue, quyền truy cập và tự động hóa như GitHub Actions. Khi bạn commit, mốc mới trước tiên có ở máy bạn. Merge và rebase: ghép lịch sử khác nhau

Nhánh tính năng của bạn bắt đầu từ A. Trong lúc bạn tạo F, nhánh main có thêm B. Muốn đưa thay đổi mới vào nhánh tính năng, bạn có thể giữ hai đường lịch sử bằng merge hoặc phát lại thay đổi bằng rebase.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

Merge trong tình huống đã phân nhánh tạo commit M nối hai lịch sử. Các commit cũ vẫn giữ ID; con trỏ của nhánh nhận merge di chuyển tới kết quả. Khi nhánh nhận chỉ cần đi tiến tới commit đã có, Git có thể fast-forward và không tạo merge commit.

Rebase phát lại thay đổi của F trên nền B, thường tạo F′ với parent mới và ID mới. Lịch sử nhìn thẳng hơn, nhưng người đã dựa trên F cần biết lịch sử đã thay đổi. Cả merge và rebase đều có thể gặp xung đột; hình đang giả định giải quyết thành công.

Nhìn hình thử trả lời

Có thể kết luận mọi lần git merge đều sinh commit có hai parent không?

Xem đáp án

Không. Một merge có thể fast-forward nếu lịch sử cho phép; tùy chọn cũng ảnh hưởng cách tích hợp.

Giới hạn cần nhớ

Tránh rebase lịch sử người khác đã sử dụng nếu chưa thống nhất cách phối hợp. Rebase không phải cách an toàn mặc định để sửa nhánh chung.

Xem sâu hơn

Sơ đồ nói về ancestry, không đo chất lượng code. Sau tích hợp, chạy lại kiểm tra trên nội dung cuối cùng. Lịch sử tuyến tính không bảo đảm các thay đổi kết hợp đúng.

Quyền Linux: ai được làm gì?

Một file có chủ sở hữu, nhóm sở hữu và các bit quyền cho owner, group, others. Với file thường, r/w/x lần lượt cho phép đọc nội dung, sửa nội dung và thực thi khi các điều kiện khác cũng cho phép. Ví dụ 640 giúp tách quyền người viết và người đọc.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

Trong dạng số, r là 4, w là 2 và x là 1. chmod 640 report.txt đặt owner đọc/sửa, group đọc, others không có quyền qua các bit này. Chủ sở hữu có thể được đổi bằng chown khi có quyền; không luôn là người đang tạo hoặc sửa file.

Với thư mục, r cho phép liệt kê tên, x cho phép đi qua/tìm entry và w cho phép sửa danh sách entry khi các điều kiện cần thiết được đáp ứng. Vì vậy quyền x trên thư mục không có nghĩa “chạy thư mục”. Việc xóa một file thường phụ thuộc quyền ở thư mục chứa nó, không chỉ bit w của chính file.

Cây thư mục Linux và vai trò từng nơi

Trên Linux, đường dẫn tuyệt đối bắt đầu từ /. Các filesystem có thể được mount vào vị trí trong cùng cây đường dẫn. Bạn đọc cây theo vai trò thư mục để biết cấu hình, dữ liệu thay đổi và dữ liệu người dùng thường ở đâu.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

/etc thường giữ cấu hình riêng của máy. /var chứa dữ liệu thay đổi trong quá trình vận hành, chẳng hạn log trong /var/log. /home thường chứa thư mục người dùng; /usr giữ phần lớn chương trình và dữ liệu dùng chung của hệ thống, không phải home của từng user.

/tmp dành cho dữ liệu tạm, không nên dùng làm nơi duy nhất giữ dữ liệu cần lâu dài. /dev chứa node thiết bị. /proc và /sys thường là các filesystem ảo để quan sát trạng thái và giao tiếp với kernel. Chúng không đơn giản là các thư mục file thường lưu trên cùng một ổ đĩa.

Git lưu snapshot và nhánh như thế nào?

Nếu quy trình Git cho biết khi nào add hay push, mô hình lưu trữ giải thích vì sao chúng khác nhau. Git lưu các đối tượng và tham chiếu; một nhánh là tên trỏ tới commit. Trong mô hình phổ biến, commit mới ghi một snapshot và liên hệ tới lịch sử trước đó.

Đọc hình: Các thẻ là các bước hoặc góc nhìn của ví dụ; đọc từ trên xuống. Mũi tên chỉ thứ tự đọc, không biểu diễn luồng mạng hoặc sự phụ thuộc bắt buộc.

Blob chứa nội dung file; tree liên hệ tên và mode với các đối tượng con. Commit tham chiếu tree và metadata như tác giả, thông điệp, parent. Khi hai commit dùng cùng nội dung, Git có thể dùng lại đối tượng thay vì sao chép mọi byte một lần nữa.

Working tree là các file để bạn chỉnh sửa. Index chọn nội dung cho commit tiếp theo. git add cập nhật index; git commit tạo commit từ index rồi thường cập nhật nhánh hiện tại. git push trao đổi đối tượng và cập nhật ref phía remote theo quyền/quy tắc của remote. Các thao tác không chỉ là “chuyển file giữa bốn hộp”.
